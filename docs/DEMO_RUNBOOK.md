# 60초 심사 데모 런북

라이브 데모의 목표는 설명보다 먼저 심사위원이 **직접 의심하고 속는 경험**을 만드는 것입니다.

## 현장 진행

| 시간 | 진행 | 화면에서 보여줄 것 |
| --- | --- | --- |
| 0~10초 | 공개 URL을 열고 새 방을 만든다 | 초대 QR과 4자리 코드 |
| 10~20초 | 심사위원 1명은 플레이어, 나머지는 관전자로 입장한다 | 익명 이름과 `LIVE` 연결 상태 |
| 20~35초 | 순한맛·AI 3명·1라운드로 시작한다 | 질문 카드와 정체를 숨긴 익명 typing |
| 35~45초 | 심사위원이 수상한 참가자에게 심문권을 쓴다 | 15초 긴급 심문 카드와 강제 답변 |
| 45~55초 | 관전자들은 인간 예측에 베팅하고 생존자는 투표한다 | 잠긴 베팅과 투표 시트 |
| 55~60초 | 최다 득표자의 최후 변론을 보여준다 | 변론 대상과 카운트다운 |

리빌과 엔딩 칭호는 60초 이후 자연스럽게 이어서 보여줍니다. 시간이 촉박하면 채팅 시간을 줄이는 별도 데모 빌드 대신 `GAME_TIME_SCALE`을 사용하지 말고, 미리 시작한 방을 준비해 두는 편이 안전합니다.

## 라이브 실패 시 복구 순서

1. 같은 공개 URL을 새로고침하고 저장된 `playerId`로 재접속합니다.
2. 방이 사라졌다면 새 방을 만들고 Mock AI로 즉시 다시 시작합니다.
3. 네트워크 자체가 불안하면 미리 녹화한 60초 영상을 재생합니다.

공개 데모 서버에는 OpenAI 키를 넣지 않아도 Mock AI가 심문·변론·투표·리빌 전체 상태 머신을 수행합니다. 실제 모델 장애가 게임 진행을 막지 않는 구조 자체도 함께 설명할 수 있습니다.

## 백업 영상 체크리스트

- 1080p 또는 세로 1080×1920, 60초 이내
- QR 입장 → 익명 채팅 → 심문 → 베팅 → 투표 → 최후 변론 → 리빌 → 엔딩 칭호 순서
- 알림, 브라우저 북마크, API 키와 개발자 도구는 화면에 노출하지 않기
- 현장 발표 PC와 클라우드 드라이브 두 곳에 각각 보관

## 플레이테스트 수치 기록

서버는 게임 종료마다 개인정보나 채팅 원문 없이 다음 집계 로그를 남깁니다.

```text
{"event":"game_complete","difficulty":"mild","winner":"HUMAN","humans":1,"aiCount":3,"roundsPlayed":1}
```

최소 20판을 모은 뒤 난이도별 인간 승률을 계산합니다. 목표 구간은 40~60%이며, 표본이 부족하면 발표 자료에 추정치를 쓰지 말고 실제 판 수와 관측값을 함께 표기합니다.

```text
자체 플레이테스트 24판 · 순한맛 인간 승률 54% · 매운맛 인간 승률 42%
```

위 숫자는 **표현 예시**입니다. 실제 로그 집계 전에는 제출 자료에 사용하지 않습니다.

## 확장 비전

스트리머 한 명이 인간으로 숨어들고 시청자 수백 명이 실시간 관전·베팅하는 방송형 파티게임으로 확장할 수 있으며, 같은 규칙을 AI 판별력과 미디어 리터러시 교육에도 적용할 수 있습니다.
